# 任务认领、进度与交接说明

日期：2026-10-10。先看 [总清单](../TASKS.md)，再看所选任务的 PRD、同名交接文件和测试用例。所有记录放在仓库，接手人无需访问私人聊天。

## 1. 认领与释放

选择任务后填写同名交接文件的认领表，至少写本人姓名/GitHub ID、认领日期、PRD 版本/hash、起点 SHA、分支/worktree、文件边界、审查人和验收人。未知字段写“待确定”，不能填一个看似真实的示例账号、PR 或测试结果。

认领文档先进入双方共享基线，再开始代码；本地尚未同步只算申请认领。任务已有人负责时，新增实施子任务需取得当前负责人同意；不覆盖原认领人。临时中断写暂停/阻塞原因，转交写交出人、接收人、接收确认日期和恢复点。

## 2. 每次工作结束都留下什么

1. 当前 PRD 版本及是否变更：具体 FR、原因、决策人/状态、影响的代码/用例/依赖任务。
2. 已完成：文件或 commit、完成到哪一步、对应 FR、可观察结果；文档完成和功能完成分开。
3. 未完成与阻塞：具体待办、依赖谁、何时可以继续；不要只写“进行中”。
4. 测试：用例是否生成/评审、自动化是否实现、是否实际运行、命令/步骤、代码 SHA、结果/日志。未运行直接写未运行。
5. 审查与验收：谁自审、谁独立审查；哪些条件已验收、哪些等用户判断；返工项不得被标为通过。
6. 下一步：下一个可执行动作、使用分支与起点、需要的环境、注意事项。运行信息脱敏，不记录 token 或私人数据。

清单状态摘要与交接明细同次更新。用例执行细节写测试文件，不在多份文档重复维护。

## 3. 需求变更规则

修改 PRD 前先记录变更原因和影响。若只澄清文字，更新补丁版本；若变更行为/验收，更新次版本并标“变更待确认”。相关测试的旧通过记录保持原版本，受影响项重新待测。

需求、实现和测试可以并行演进，但不能静默更换验收目标。接口影响其他任务时在双方交接记录写同步结论。被排除的需求进入总清单候选或历史待办，不埋在聊天里。

## 4. 最低完成条件

- 本期 FR 的验收逐项有事实；未实施的增强项明确标后续，不混入本期完成声明。
- 用例已评审，必要自动化和真实场景均实际执行；失败/未测项有明确处理，不用“整体通过”掩盖。
- 代码审查和人工产品验收分别记录，交接中的待办、风险、回滚方式清楚。
- 合并与发布另有事实字段；“完成开发”不表示已推送、已合并或已发布。
- 交接负责人确认接收；若没有接收人，保持待交接，而不是自动关闭。
