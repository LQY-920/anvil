# T04 · 内部频道、线程与 @Agent PRD

版本：1.0；日期：2026-10-10（Asia/Shanghai）；状态：需求初稿，待评审、待认领。  
入口：[总清单](../TASKS.md) · [交接记录](../handoffs/T04.md) · [测试用例](../tests/tasks/T04-testcases.md) · [公共边界](COMMON.md)

## 1. 摘要

在 Anvil 内加入频道、线程和明确的 @Agent 派活操作。用户在同一上下文中讨论、启动任务、查看结果、反馈续作；看板继续提供全局状态。用户已选择内部交互，首期不接真正的 Slack。

## 2. 现状与问题

目前以看板/Issue 面板为主，已有评论可能通过 enqueueForComment 排队成为指令。消息流主要是 Task 执行日志，不是完整聊天模型。WS 重连不能保证历史补齐；若把普通聊天直接接到旧评论端点，会误派任务，刷新/重发也可能重复执行。

## 3. 目标与指标

| 目标 | 验收标准 |
|---|---|
| 意图清晰 | 普通消息、引用、代码块、编辑和 Agent 输出均不触发执行；派活有明确预览和提交动作 |
| 一次命令一次执行 | 网络重试、重复点击和刷新保持同一 command_id/Task；不同 payload 冲突可见 |
| 上下文连续 | 线程可追溯 Issue、各轮 Task、报告/验证和当前待处理状态 |
| 可恢复 | 断线重连按持久化游标补齐，无重复显示或漏掉最终状态 |

## 4. 用户、范围与非目标

面向本机工作台使用者与协作者分别使用各自 Anvil 实例。频道按项目/用途组织，Agent 是执行对象而非频道。可有纯讨论线程；任务线程对应一个 Issue，多次 Task 保留在同一线程。
范围含频道、线程、文本消息、派活、续作、状态卡片、待处理与深链接。排期建议 T03 后，设计可提前。不包含真正 Slack/Discord、多人实时权限体系、语音视频、跨 Agent 自主群聊、任意聊天自动调工具。

## 5. 功能需求

### T04-FR01 频道与线程（P0）
- [ ] 创建/选择项目频道，查看线程和历史；频道、草稿和仓库上下文不跨项目串用。
- [ ] 讨论线程可不创建 Issue；首次派活后关联唯一 Issue，后续各轮关联 Task/工作树与源消息。
- [ ] 旧看板任务仍可访问，线程、任务面板和看板显示同一任务状态。

### T04-FR02 明确派活（P0）
- [ ] 默认“发送”只保存讨论；选择 @Agent 后进入派活草稿，提交前显示仓库、目标、验收标准、Profile/流程和执行动作。
- [ ] 只有点击明确“派发任务”才执行；纯文本 @、引用/代码块、编辑历史消息、导入消息与机器人回复不执行。
- [ ] 缺仓库/可用 Profile/验收要求显示可纠正的阻塞，不能静默使用上一个项目。

### T04-FR03 命令幂等与追溯（P0）
- [ ] 每次派发由客户端预先生成稳定 command_id；服务端保存 payload_hash、来源消息和结果 Task。
- [ ] 同一键同一输入返回原结果，同键不同输入返回 409；超时先查结果再重发。
- [ ] 消息、命令、Issue、Task、流程实例互相可查；服务端原子建立关联，不能显示成功却无任务。
- [ ] 同一讨论线程的不同命令并发首次派活也只能绑定一个 Issue；使用事务及唯一约束。已有 pending 时明确返回关联 Task 的合并结果，或返回可解释冲突并保留未提交草稿，不能将 insertQueuedTask 的 null 当成功丢掉输入。

### T04-FR04 讨论与追加执行（P0）
- [ ] 输入区区分讨论和追加指令；运行中追加绑定 expected_task_id/执行代次，终态返工才要求 expected_head；无最终 HEAD 时也可正确排队。
- [ ] 正在执行时使用排队接力，展示“已排队，当前运行完成后执行”，不伪装为注入运行中 CLI。
- [ ] 不丢弃既有 pending 指令，不在后台切换 Provider；需要合并或替换时显式说明并保留记录。
- [ ] 提交时冻结指令内容及其来源轮次，前序结束后由 Runner 准备并记录接续的最终锚点；前序失败或锚点不完整时阻塞并显示原因，不把旧 Task 的反馈串到最新 Task。

### T04-FR05 结果和待处理卡片（P0）
- [ ] 执行日志折叠；卡片分别显示运行、交付、验证、审查和远端合入，不用一句“完成”掩盖失败。
- [ ] 结果链接既有 Diff、Report、Verification、PR/裁决入口；返工复用既有契约，不新建弱化 Gate 的批准路径。
- [ ] 待处理聚合失败、阻塞、待审与需输入，通知去重，跳转到准确 Task 而非仅 Issue 最新轮。

### T04-FR06 历史兼容（P0）
- [ ] 新讨论使用新语义/端点，不调用旧评论即指令通路；历史记录只读迁移不重放命令。
- [ ] 旧入口如继续保留，明确标注它会追加执行指令，保持 API 兼容并记录迁移版本。
- [ ] 老 Task 消息流保留为日志来源，不能冒充人类频道消息；迁移可回滚、不删除交付证据。

### T04-FR07 断线恢复和定位（P0）
- [ ] 消息/命令状态持久化，按稳定事件序号和分页游标读取；WS 为提示，重连通过 REST 补齐权威状态。
- [ ] 草稿保存在正确项目/线程，断线显示未发送或发送结果待核对；不能把本地占位当服务端确认。
- [ ] 刷新和深链接可恢复线程及目标 Task；重复事件去重，顺序缺口触发补齐。

以上为首期核心。富文本附件、搜索、真实 Slack 连接作为新任务另立范围。

## 6. 非功能需求

长线程分页，默认不加载全部日志；文本安全渲染，不执行消息内 HTML/脚本。消息体及查询有大小上限；排序稳定，键盘可提交/取消明确操作。至少测 1,000 条 fixture 消息的分页与定位，不承诺未经实测的性能数值。沿用本机部署边界，移动远程由 T05 完成认证。

## 7. 架构与边界

Core 新增会话/命令协议；Server 持久化消息并调用现有 Issue/Task/流程服务；Web 加频道与线程视图、统一状态呈现。Runner 与 Adapter 不需要知道“Slack”。任务生命周期继续以 Task/Report/Git/Decision 为权威，聊天只是入口与展示。
复用既有 seq/幂等设计但区分频道消息序号与 Task 日志序号，不能混用。

## 8. API、鉴权与错误（拟议）

| 操作 | 输入 | 输出 |
|---|---|---|
| GET/POST /api/channels | project_id / name | 频道列表/频道 |
| GET /api/threads/:id/messages | before/after_cursor、limit | 消息及稳定游标 |
| POST /api/threads/:id/messages | client_message_id、body、kind=discussion | 已确认消息；不创建 Task |
| POST /api/threads/:id/dispatch | command_id、source_message_id、仓库/Profile/目标 | command、issue_id、task_id |
| POST /api/threads/:id/follow-up | command_id、文本、expected_task_id；终态返工另带 expected_head | 下一任务/排队结果 |
| GET /api/commands/:id | 命令 ID | pending/applied/rejected 和原结果 |

派发请求例：`{"command_id":"cmd-1","source_message_id":"msg-1","repository_id":"repo-1","profile_id":"codex-local","goal":"修复问题","acceptance":"指定用例通过"}`。
响应例：`{"command_id":"cmd-1","state":"applied","issue_id":"issue-1","task_id":"task-1","replayed":false}`。
缺上下文 422、对象不属于项目 404、同键不同内容或 HEAD 变化 409、服务暂不可用 503。超时保留 command_id 查询结果。人类写入与 task token 分离；T05 前仅本机调用，远程会话统一接 T05。

## 9. 数据模型（拟议）

| 类型 | 字段与约束 |
|---|---|
| Channel | id:string、project_id:string、name:string、created_at；唯一归属项目 |
| Thread | id、channel_id、issue_id?:string、title、last_event_seq:number；首次派发在事务中唯一绑定 Issue，冲突回读已绑定结果 |
| ConversationMessage | id、thread_id、client_message_id、author_kind:human/agent/system、kind:discussion/command/result、body、seq、created_at/edited_at |
| DispatchCommand | id、thread_id、source_message_id、kind、payload_hash、state、result_task_id?、error_code?；命令 ID 唯一 |

ConversationMessage 与已有 TaskMessage 分表/分协议；结果卡片引用证据而非复制报告全文。编辑消息保留修订记录，不改变已提交命令。

## 10. 交互与状态

频道列表 → 线程 → 输入区；讨论和派活模式有清楚文案，派活预览再提交。右侧或内联结果卡片显示进展，展开才看日志。空频道提供开始讨论/创建任务；加载、离线、发送未知、排队、等待审查各有状态；屏幕阅读器能读出状态变化。
保留看板路由及深链接。移动布局在 T05 细化，本期避免把所有功能锁死在固定三栏。

## 11. 集成与用户决策

本任务依据用户对截图第 4 点的明确澄清：先在 Anvil 内做频道、线程、@Agent 派活。无需 Slack OAuth 或 Slack bot；若后续需要外部连接，另加任务并复用本期命令协议。
复用 T01 裁决、T02 Profile、T03 可选流程选择；缺某项能力时 UI 明确不可用，不伪装接通。

## 12. 边界情况

| 场景 | 预期 |
|---|---|
| 代码示例含 @codex | 仅文本，无 Task |
| 快速双击/离线重发 | 同一命令只建一项任务，返回原结果 |
| 派活后编辑源消息 | 任务输入快照不变；新指令需另发 |
| 运行中连续反馈 | 可见排队语义、不丢顺序、不假装实时打断 |
| 断线错过 complete 事件 | REST 补齐最终状态及结果 |
| 旧评论导入或切换项目 | 不重放执行，不串草稿或仓库 |

## 13. 测试与完成标准

[测试用例](../tests/tasks/T04-testcases.md)覆盖无误派、幂等、顺序、旧版兼容、断线补齐、日志安全和定位。端到端至少验证：新线程派活、先讨论再派活、运行中反馈续作；同时观察 Task 数量及输入快照，不只看界面截图。
全部 FR、产品测试/build/四包类型检查、自审/独立审查、产品验收通过，且普通讨论从不触发旧 enqueueForComment，才可完成。远程多用户/手机支持不在本期通过范围内。

## 14. 实施顺序与交接

先定消息/命令语义和迁移策略，完成服务端幂等与历史兼容测试，再做频道线程 UI、状态卡片和重连，最后执行端到端验收。每轮交接记录讨论/指令边界、迁移版本与回滚办法。
认领时确认频道默认组织、输入区文案、旧评论入口保留方式和独立审查者；不据此扩大到多人 SaaS。
