## 2. 怎么选、怎么推进

1. 阅读本清单和 [公共边界](prds/COMMON.md)，选择一个 PRD，核对其前置条件、范围和验收。
2. 在对应交接记录填认领人、日期、使用的 PRD 版本/hash、起点 SHA、分支/worktree、文件范围、审查/验收安排；在清单同步状态。
3. 认领先以一条独立文档变更进入双方共享基线，再开始代码，避免两人同时占用同一任务。尚未共享的本地填写只算“认领申请”；有冲突先协商，不用覆盖记录抢占。
4. 认领人完成需求评审与技术拆分；开发、测试、审查、验收分别记录，不用一个百分比代替事实。
5. 每个工作段结束、需求修改、测试失败/恢复、准备交接、准备验收或合入后都更新交接记录。规则和模板见 [交接说明](handoffs/README.md)。

两人可以分别认领 T01/T02。暂未满足依赖的任务仍可评审和设计，不能把假数据演示写成集成完成。

## 5. 状态与证据规则

- 认领：待认领 → 申请认领 → 已认领 → 已交接/释放。负责人更换须双方记录，不清除前任历史。
- 研发：未开始 → 需求评审 → 设计 → 开发 → 待联调 → 待验收 → 完成；阻塞/暂停单列原因和恢复条件。
- 需求：初稿/已评审/变更待确认/已确认；记录版本与 hash，不能用“无变化”覆盖之前的修订。
- 测试：用例未生成/初稿/已评审；自动化未实现/部分/已实现；执行未运行/部分通过/失败/通过。结果必须有代码 SHA、环境、命令或步骤、执行人、时间和证据链接。
- 审查与验收：自审、独立审查、产品验收、联合验收、合并、发布分别记录。代码写完或测试通过不自动代表验收完成。
- “完成”要求本期所有验收项与必要测试有证据，缺陷有明确结论，交接清楚；未合并也须标明未合并。合并/发布状态不能从研发状态推断。

## 6. 后续如何更新方向

新增方向在本清单追加 T07、T08……，不重编号旧任务。每项创建独立 PRD、交接记录和用例文件，并写明优先级、依赖、验收人；未决定实施的想法标“候选”。不要把新想法顺手塞进正在开发的任务。

范围变化更新对应 PRD 版本、变更摘要、影响的 FR/用例/共享接口，并在交接记录记录决策人、日期及重新验收范围。旧通过结果绑定旧 SHA/需求版本，不能搬到新版本。中止或替代任务保留状态和理由。
